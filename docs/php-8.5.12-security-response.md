# PHP 8.5.12 セキュリティリリース対応記録

作成日: 2026-10-21

## 1. 背景

PHP 8.5.12 がセキュリティリリースとして公開された（NEWS 日付: 2026-10-22）。
本プロジェクトのバックエンドは PHP 8.x（php-fpm + nginx、Render / ローカル Docker）で動作するため、影響を調査した。

## 2. 脆弱性による問題点

| ID | 内容 | 想定される影響 |
|---|---|---|
| GHSA-w8hw-w9fx-j79w（CVE-2026-109618） | メモリ不足（OOM）時に `longjmp()` で処理を抜けるため、リクエストのメモリが不正な状態のままシャットダウン処理に渡る | 認証なしのリモートコード実行（RCE）。マルチパートリクエストが主な入口 |
| GHSA-6wmf-4rv5-p3rp（CVE-2026-109619） | 前のリクエストの状態が残り、後続リクエストの初期化前に参照されて use-after-free が発生する | 巧妙なヒープ配置による RCE |

- 2件は組み合わせて対処する必要がある（公式アドバイザリより）。
- 完全な対策は **修正版 PHP への更新のみ**。設定による緩和は被害を減らすが完全ではない。

### 本プロジェクトへの影響評価

- **FPM 構成:** 起動時の OOM では子プロセスが終了するため安全。通常処理中の OOM は影響を受けうる（「完全な攻撃は FPM では未実証」と記載）。
- **攻撃の入口:** 稟議作成・更新 API（`POST /api/approvals`）がファイル添付（マルチパート）を受け付ける。
- **CVE-2026-109619:** FPM では nginx から `PHP_VALUE` を渡す構成でないと成立しにくい。`backend/docker/default.conf` では渡していないため限定的。
- **到達性:** Render の API は共有シークレット（`API_PROXY_SECRET`）で Vercel 経由のみに制限しているが、Vercel 経由であれば誰でも到達できる。攻撃は届く前提で考える。
- **被害の大きさ:** データはダミーのみ。ただし RCE が成立すると、環境変数（DB パスワード、`APP_KEY`、`API_PROXY_SECRET`）が読まれる恐れがある。踏み台利用や無料枠停止のリスクもある。

総合評価: **深刻度は高いが、ポートフォリオ用途（ダミーデータ）のため被害は限定的。緊急停止するほどではない。**

## 3. 対応方針の比較と決定

### 比較した選択肢

| 案 | 内容 | メリット | デメリット |
|---|---|---|---|
| A. 公式イメージの 8.5.12 を待つ | Dockerfile は `php:8.5-fpm-alpine` のまま、公開後に再ビルド・再デプロイ | 安全で手間が少ない。構成を公式に揃えたまま保てる | 公開までの間は未修正の状態が続く |
| B. Dockerfile で php.net のソースをビルド | `php-8.5.12.tar.xz` を取得し、checksum を検証してビルド | すぐ 8.5.12 にできる | ビルドが長い（10〜20分）。Render 無料プランで失敗するリスク。configure オプションが公式と異なり保守負担が増える |
| C. ソースの zip をリポジトリに入れる | 手元の zip を Git に追加 | ネットワーク取得が不要 | 約35MBが履歴に永続的に残る。非推奨 |
| D. 設定による緩和のみ | アップロード関連の上限を絞る | 即時に入れられる。副作用が小さい | 完全な対策ではない |

### ソースビルドについて（補足）

- 手元の `php-8.5.12-src.zip` は、GitHub の `php-8.5.12` タグと内容を比較し、差異がないことを確認した（zip にのみ入っている生成済みパーサファイル28件を除く）。ローカル検証には使用可能。
- ただし Render は手元ファイルを参照できないため、ローカルで検証できても本番反映には使えない。

### 決定

- **A + D を採用する。**
  - 被害がダミーデータに限られ、攻撃条件も限定的なため、ソースビルドで急ぐリスク（ビルド失敗・保守負担）の方が大きいと判断。
  - 公式イメージの公開までは、設定による緩和（D）で攻撃面を狭める。

## 4. 最終的に行う対応

### 4.1 実施済み

| 項目 | 内容 |
|---|---|
| PHP バージョン | `backend/Dockerfile` を `php:8.5-fpm-alpine` に、CI（`.github/workflows/backend-deploy.yml`）を `php-version: '8.5'` に変更。ローカルで 8.5.11 を確認し、全40テスト通過 |
| PHP 設定（`backend/docker/php.ini`） | `max_file_uploads=10`、`max_input_vars=1000`、`max_input_nesting_level=16`、`max_input_time=30` を追加（`post_max_size=210M` はアプリ上限の 20MB × 10 件に合わせて維持） |
| nginx（`backend/docker/default.conf`） | `client_body_timeout 30s`、`client_header_timeout 15s`、`large_client_header_buffers 4 8k` を追加（`client_max_body_size` は 210M を維持） |
| 動作確認 | ローカルで再ビルドし、設定値の反映・nginx 設定テスト・`/api/health`・ファイル添付付きの申請作成を確認 |

### 4.2 今後の対応

1. 公式イメージ `php:8.5.12-fpm-alpine`（または `8.5-fpm-alpine` の更新）の公開を確認する。
2. ローカルで `docker compose build --no-cache backend` を実行し、`php -v` が 8.5.12 であることを確認する。全テストを実行する。
3. Render の **新旧2サービスとも** 「Clear build cache & deploy」で再デプロイする（GitHub Actions の Deploy Hook でも可。ただしキャッシュが残るため、手動の方が確実）。
4. `/api/health` と画面の動作を確認する。

### 4.3 余裕のあるときに実施（任意）

- Supabase の DB パスワードと `APP_KEY` の再発行（Render の環境変数とローカル `.env` を更新し、再デプロイする）。
  - 目的は、**過去に漏れた可能性のある古い値を無効化すること**。今後の脆弱性による漏えいを防ぐものではない（新しい値も、サーバーが乗っ取られれば盗まれる）。PHP の脆弱性への根本対策は 4.2 の更新のみ。
- `composer audit` で依存パッケージの既知の脆弱性を確認する。

## 5. 注意事項

- 設定による緩和は被害を減らすだけで、完全な対策ではない。更新が完了するまでは未修正の状態であることを認識しておく。
- 添付の上限はアプリ側で 1 ファイル 20MB・最大 10 件（`StoreApprovalRequest` / `UpdateApprovalRequest`）。上限を引き上げる場合は、PHP と nginx の設定も合わせて見直す。
